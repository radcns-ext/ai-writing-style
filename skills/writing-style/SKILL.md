# writing-style — 커밋 메시지·주석 문체

코드에 남기는 글은 크게 두 가지, 커밋 메시지와 주석이다. 둘 다 결국 **나중에 이걸 다시 보는 사람이 "왜 이렇게 했지?" 를 알 수 있게** 하려고 쓴다. "무엇을 바꿨는지" 는 diff 와 코드가 이미 보여주니까 굳이 반복할 필요가 없다.

톤은 옆자리 동료한테 설명하듯이 잡는다. 보고서나 명세서처럼 딱 끊어 쓰기보다, "이래서 이렇게 했다" 가 자연스럽게 읽히면 된다. 기계가 요약한 티가 나지 않는 게 목표다.

### 아이콘·이모지는 쓰지 않는다

커밋 메시지, 주석, PR 설명 어디에도 아이콘이나 이모지를 넣지 않는다. 🚀 ✨ 🐛 ✅ ⚠️ 같은 이모지는 물론이고, gitmoji 코드(`:sparkles:`, `:bug:`), 체크 표시나 장식용 기호(✔ ✘ ★ ▶ ➜ ●)도 마찬가지다. 사람이 손으로 쓴 글에는 이런 게 거의 안 들어가서, 하나만 있어도 바로 티가 난다. 강조나 경고가 필요하면 말로 쓴다. 주석이라면 `주의:` 로 시작하면 된다.

---

## 1. 커밋 메시지

### 말하듯 쓴다

- 본문은 평범한 문장으로 쓴다. "~해서 ~했다", "~라서 ~로 바꿨다" 처럼 원인과 결과를 이어주면 훨씬 사람 냄새가 난다.
- 명사로 뚝 끊는 개조식("추가.", "마련.", "반영.")만 이어지면 딱딱하게 읽힌다. 제목은 짧게 끊어도 괜찮지만, 본문까지 그렇게 쓰지는 않는다.
- 겪은 일을 그대로 쓰면 된다. "생각보다 원인이 단순했다", "일단 막아두고 근본 수정은 따로 한다" 같은 말도 충분히 들어갈 수 있다.
- 다만 너무 가볍게 풀어지지는 않게. 느낌표나 "드디어!" 같은 감탄은 넣지 않는다.

### 피하면 좋은 것들

| 이렇게 쓰는 대신 | 이렇게 |
|---|---|
| `[Feat]` `[Fix]` 같은 태그 (프로젝트가 원래 쓰고 있다면 따른다) | 그냥 문장으로 시작한다 |
| 엠대시 `—` 로 제목 뒤에 부연 붙이기 | 부연이 필요하면 본문으로 내리고, 아니면 빼도 된다 |
| 제목 길이를 매번 비슷하게 맞추기 | 짧으면 짧은 대로 둔다. 8자짜리 제목도 충분히 좋은 제목이다 |
| 모든 커밋에 본문 달기 | 제목만으로 충분하면 제목만 써도 된다 |
| 본문을 항상 불릿으로 나열 | 두세 문장 평문이 기본이다. 항목이 정말 여러 개일 때만 불릿을 쓴다 |
| "~하도록 수정", "~문제 수정" 반복 | 무슨 일이 있었는지 그대로 쓰면 매번 자연스럽게 달라진다 |
| 개조식 종결("추가.", "마련.")로 통일 | 평서문 위주로, 종결어미가 한 가지로 굳지 않게 |
| `검증: 148/148` 같은 정형 라인 | 테스트 수치는 대부분 커밋에 남길 필요가 없다 |
| 제목 앞에 이모지·gitmoji(`✨`, `:bug:`) 붙이기 | 아무것도 붙이지 않고 문장으로 시작한다 |
| AI 도구 푸터(`Co-Authored-By`, `Claude-Session`, `Generated with`) | 넣지 않는다 |

### 확인한 것만 쓴다

마이그레이션 번호, 파일명, 함수명, 테이블명, 티켓 번호는 **기억이나 짐작으로 쓰지 않는다.** 실제 diff 나 파일에서 확인한 것만 적고, 확인이 안 되면 그 식별자는 빼고 풀어서 쓴다. "V121 컬럼 추가" 라고 써놨는데 실제로는 V123 이었다면, 그 커밋은 이력에 틀린 정보를 계속 남기게 된다.

### 좋은 예

```
주문 기간검색에서 마지막 날짜가 빠지던 문제

toISOString 을 쓰다 보니 UTC 로 밀려서 31일 주문이 검색에 안 걸리고 있었다.
KST 오프셋을 고정해서 해결했다.
```

```
카탈로그 삭제된 주문도 목록에 표시
```

```
관리자가 파트너사 명의로 주문 대리 등록

메뉴는 SUPER_ADMIN 전용으로 따로 뺐다. 파트너 쪽 화면에는 대리 등록이라는
표시가 뜨고, 취소나 재주문은 할 수 없게 막아뒀다. 알림 메일은 일부러 보내지 않는다.
```

### 아쉬운 예

```
[Feat] 관리자 대리 주문 등록 기능 — DB/메뉴/Lambda

관리자가 특정 파트너사 명의로 주문을 대신 등록할 수 있는 기반을 마련.
- orders.proxy_admin_id 컬럼 추가 (V121)
- SUPER_ADMIN 전용 대리 주문 메뉴 신설
- Lambda 3종에 대리 모드 분기 추가
```

태그, 엠대시 부연, 개조식 종결, 기계적인 불릿, 확인 안 된 마이그레이션 번호가 한꺼번에 들어 있다. 읽어보면 뭘 했는지는 알겠는데 왜 그렇게 했는지는 안 보인다.

### 여러 개로 나눌 때

- **기능 단위로 나눈다.** 백엔드/프론트 같은 영역이 아니라 "무엇이 달라졌나" 로 묶는다. 한 기능이 DB·API·화면에 걸쳐 있으면 그건 커밋 하나다.
- 나눈 결과는 커밋하기 전에 **목록으로 먼저 보여주고 확인을 받는다.**
- 형식은 일부러 조금씩 다르게 둔다. 8개가 전부 같은 틀이면 그것만으로도 티가 난다.

### 커밋 전에 한 번 훑어보기

- 제목에 `—` 가 들어갔나
- 아이콘이나 이모지, 장식 기호가 섞여 있나
- 제목 길이가 다 비슷비슷한가
- 본문이 전부 불릿인가
- 종결어미가 전부 똑같은가
- 읽었을 때 보고서처럼 딱딱하게 느껴지나
- 확인하지 않은 번호나 이름이 섞여 있나

걸리는 게 있으면 고쳐 쓴다.

### 커밋 실행은 별개

이 스킬은 **메시지를 어떻게 쓰는지** 만 다룬다. `git commit` 을 실제로 할지는 사용자가 명시적으로 요청했을 때만 한다. 메시지를 잘 써놨다고 해서 알아서 커밋하지는 않는다.

## 2. 주석

코드가 이미 말하고 있는 걸 또 쓸 필요는 없다. 주석은 **코드만 봐서는 알 수 없는 것**, 그러니까 왜 이렇게 했는지, 건드리면 뭐가 깨지는지, 그 근거가 뭔지를 남기는 자리다. Java/Kotlin/Swift/JS/Python 모두 같은 기준이다.

### 기준

1. 아이콘·이모지·장식 기호는 쓰지 않는다. 경고가 필요하면 `주의:` 로 시작한다.
2. "무엇" 보다 "왜" 를 쓴다.
3. 함정이나 건드리면 안 되는 부분은 `주의:` 한 줄로 이유와 함께 남긴다.
4. 결정에는 근거를 하나 붙여둔다 (날짜, 이슈 번호, changelog 번호 중 하나면 충분하다).
5. 짧게 쓴다. 한 줄로 되면 트레일링 주석(`// ...`)으로.
6. 한국어 평서체로 쓴다. "~마라", "~할 것" 같은 명령조보다 "~하면 ~된다", "~라서 ~했다" 처럼 이유가 보이게 설명하는 쪽이 읽기 편하다. 확인 안 된 내용은 "추정" 이라고 밝혀둔다.

### 예시

의도와 근거:

```java
// 관리자 refresh 는 유휴 30분 sliding 으로 둔다. 직원 계정과 정책을 분리했다(2026-08-29).
private int adminRefreshTokenExpirationMinutes = 30;
```

함정:

```swift
// 주의: 여기서 super openURL 을 부르면 isa-swizzle 때문에 무력화돼서 크래시가 난다(2026-09-02 확인).
```

계산 근거 (숫자가 어디서 나왔는지):

```css
/* 98px = 썸네일 110px − 좌우 margin 6px×2. 썸네일 폭이 바뀌면 여기도 같이 바꿔야 한다. */
.badge { max-width: 98px; }
```

### 피하면 좋은 것들

- 아이콘, 이모지, 장식 기호(⚠️ ✅ ★ ▶ 같은 것)
- 코드를 그대로 다시 읽어주는 주석 ("count 를 0으로 초기화")
- 죽은 주석 (주석 처리된 옛 코드, 지금 동작과 안 맞는 설명)
- 근거 없는 TODO ("나중에 고치기")
- 작성자 서명이나, 날짜만 있고 내용은 없는 헤더
